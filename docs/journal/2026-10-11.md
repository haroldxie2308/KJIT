### Semantics

Faults (`exp_simd_fault`, EL0, 3 identical boots; two pages, the second PROT_NONE, access
crosses at byte k; LDTR/STTR are plain accesses at EL0 and fault the same way):

- Native on this CPU: a load that faults leaves the faulting register untouched and
  has already written every register it completed (`ldp q0,q1` with q1 faulting: v0
  changed 16 bytes; `ld1 {v0-v3.16b}`: 16-byte units); a store has written every whole
  16-byte register it completed and none of the faulting one (`str q` crossing at k = 8
  writes 0 bytes).
- C3, all pieces to scratch first: no V register is ever written at a fault (cleaner than
  native; the Mem exit re-executes natively, which redoes the load). Stores: memory is
  written in 8-byte units (`str q` at k = 8/12 wrote 8 bytes, `stp q` at k = 24 wrote 24).
  Native re-execution rewrites them with the same data; as for the GPR pair lowering (two
  STTR) A5 already accepts.
- C3 with one scratch (`c3s`): a half-loaded q register is visible (low half new, high
  half zero, the `fmov d` zeroes it): v0 changed 16 bytes at k = 8, `ldp` k = 24 changed v0
  and v1 where native changed v0. Harmless after native re-execution, but not "state before
  the instruction"; the differential oracle would see it at the exit.
- C0/C1/C2: the same instruction executes, so the footprint is native's.

Single-copy atomicity (Arm pseudocode, ISA_A64_xml_A_profile-2026-03
`shared_pseudocode.xml`, `aarch64/functions/memory/Mem`): a 16-byte SIMD&FP load/store that is
8-byte aligned is two 64-bit single-copy-atomic accesses, in any order, before the FEAT_LSE2
rule is consulted; a 32-byte `LDP`/`STP` (SIMD&FP) aligned to 8 is four 8-byte accesses (a
single 32-byte access only with FEAT_LS64WB and 32-byte alignment); `LD1` is per element;
`ldr d/s` is one access of that size. So 64-bit LDTR/STTR pieces keep the architectural
atomicity of every 8-byte-aligned q/d/s access. Not 8-aligned: the architecture promises
nothing but implementation-defined atomicity inside an aligned granule >= 16 bytes
(LSE2 `MemSingleGranule`), which C3 loses. Preconditions for C3: FEAT_LS64WB absent
(`ID_AA64ISAR1_EL1.LS64 < 4`, 0 here), pin it at module init like A7c pins LSE2.

Scratch (pool x12..x15): C3 loads, all-pieces-first: `ldr b/h/s/d` 1, `ldr q` 2, `ldp s/d` 2,
`ldp q` 4, `ld1` 1-2 registers 2-4 (plus a base fill: the last LDTR may overwrite the base
scratch if the base needs no writeback; plus the SP-check scratch shared with a data
scratch), `ld1` 3-4 registers 6-8: do not fit, stay Unsupported or take `c3s`. Stores need
1-2 whatever the register count. C0/C1/C2 keep today's 3-4. Code size per access:
C0 6-7 words, C1/C2 4 (+2 per window for C1), C3 2 (d/s), 4 (ldr q), 8 (ldp/stp q), 16
(4-register LD1/ST1). Coverage: C3 can lower every in-scope load/store, the register-offset
and literal forms (address into scratch first), LDNP/STNP, LD1R and lane forms, `dc zva`
(eight `sttr xzr`), and cannot lower LD2-LD4 (de-interleave) or anything needing a vector
temporary. C2 (privileged access) covers every form including LD2-LD4, because the original
instruction runs on a range-checked address.

### C2: what a safe version needs, and the run-scoped form

A region window inside a fragment (a loop across its back-edge) needs: a PAN-state
dataflow in the verifier (every word of the region known PAN-clear, joins from outside
rejected), a PAN-restoring variant of every exit that can be reached from inside (Mem
stubs, budget stub, template miss, the fall-out to the epilogue), the budget `cbz` inside the
region going to such a stub, the fault-site entries of LDTR/STTR and window accesses inside
naming PAN-restoring stubs, region entry/exit insertion at layout (natural-loop
detection), and no `BL`/`BLR`/`BR`/`RET` templates inside. Interrupts are fine at init's
`SCTLR_EL1.SPAN == 0`: exceptions enter with PAN set and `ERET` restores the clear PAN.
That is a large verifier and layout change for one window per loop.

The run-scoped form has none of that: the A13 bracket (`kjit_call_fragment_fpsimd`)
clears PAN with one `msr pan,#0` right before `kjit_call_fragment` and sets it right
after it returns. Every exit of a fragment run already funnels through the epilogue `ret`
to that one place (budget exit, `Mem`/fault stubs after the fixup, runtime exits); the
verifier only has to require the range check before each privileged access and forbid
`msr` altogether. Why it is no weaker: with PAN clear the verifier's rule 3 still limits
every plain load/store to the kernel frame, `pt_regs` and the dispatch table, so no
unverified instruction can touch user memory; PAN never protected kernel memory. A
kernel-mode loop with PAN = 0, interrupts and preemption enabled and no call in it
(`exp_simd_panirq`, 300 ms on cpu1 and cpu2 with a busy task on the same CPU): the loop
read PAN 2.3e8 times and never saw it set; 302/302 and 303/303 1 ms hrtimer interrupts hit
the PAN = 0 context, and in all of them the handler saw PAN = 1 (SPAN = 0) and the
interrupted SPSR had PAN = 0; 38 involuntary preemptions of the loop, PAN stayed clear
across them; no migration. The cost is the same per run, not per access: `msr pan,#0;#1`
4.1 ns, plus 3.0 if the code between them follows a branch.

### C4: features and kernel facts (`exp2ids`, boots F1-F3, M1/HVF guest)

FEAT_LSE2 (ID_AA64MMFR2.AT = 1) and LSE, LRCPC2, CRC32 present; PAN2 (MMFR1.PAN = 2), UAO
present, EPAN off, SPAN = 0, nAA = 0, A = 0; DCZID_EL0 = 4 (64 B block, DZP = 0); no
LSUI (ISAR3.LSUI = 0), no MOPS (ISAR2.MOPS = 0), no LS64 (ISAR1.LS64 = 0), no SSBS, MTE,
SVE, SME, BTI. The guest hides nothing that would help; FEAT_LSUI is the hardware fix
(`LDTP/STTP/LDTNP/STTNP Qt1,Qt2` are unprivileged SIMD&FP pairs in the 2026-03 XML; no
single-register q form) and FEAT_MOPS has unprivileged copy/set variants (`CPYFPWT*`,
`SETPT*`); neither exists on this host. `FEAT_UAO` goes the wrong way (makes LDTR
privileged). The register form of `msr PAN` is 5x slower than the immediate. Kernel
config: `ARM64_SW_TTBR0_PAN` off, `ARM64_EPAN` off, 48-bit VA, PREEMPT, no SVE/SME.

### Ranking and recommendation

Speed = geometric mean of the six loop slowdowns, plus the per-access cost; contract =
what A9/A8 promise today.

| rank | candidate | speed | contract kept | needs |
|---|---|---|---|---|
| 1 | C2 run-scoped (PAN cleared by the bracket) | 1.37x; 0.2 ns/access | all of A9 (the same instruction runs: footprint, atomicity, even LS64WB); defence in depth for plain accesses is given up (analysis above) | trampoline `msr pan`, verifier rule 8 shrinks, PAN windows and PAN stubs disappear from reg-virt/layout/rephrase |
| 2 | C3 | 2.32x; 0.2-0.86 ns/access | PAN invariant and every verifier rule; atomicity exact for 8-aligned (pseudocode), store footprint 8-byte granules, V state clean | new reg-virt lowering, scratch limits (LD1 3-4 regs), code x2-4, LS64WB init check |
| 3 | C1 | 14.2x; 1.0-5.0 ns/access | A9 shape | verifier window generalisation; still 9-24x on loops, window sits behind every back-edge |
| 4 | C0 today | 29.9x; 7.6 ns/access | A9 | none |

Recommendation: C2 run-scoped. It is the fastest, keeps the access instruction native
(no new atomicity or fault argument), covers every SIMD&FP memory form (LD2-4, register
offset, `dc zva` need no lowering other than the address), and the same change would
take LSE atomics out of windows (not measured here). Its price is one new kernel
invariant (PAN clear for a bracketed run). If that is refused, C3 is the fallback; do
not build C1 (14x) or loop-scoped C2. Cheap and useless alternatives: reordering today's

### Conclusion

1. The loss is in the fragment code, not in the runtime entries: 5.8x the native time for the same code
   (4.59 against 0.79 us SET). Entries and bracket are 0.35 us of 4.15 us of positive rows (SET); the
   Unsupported exits and the native tails are noise.
2. Dispatch is the biggest category: 2.29 us SET / 1.91 us GET (55% / 53% of the positive rows), of
   which 0.47 / 0.39 us is the template words and 1.82 / 1.52 us the stall after the jump. It costs about
   5 ns per call target and per return target (350 / 298 transfers per request), where the loop
   microbenchmark of one site measured 0.4 ns. Distinct call sites and polymorphic targets cost 3.7 ns
   per transfer in the `sites` and `foot` microbenchmarks, so most of it reproduces in a microbenchmark;
   what is left in redis is 1.0 / 0.8 us. An optimization that makes a transfer cost what it costs
   natively would remove 1.8 us (stalls) to 2.3 us (stalls and template words) of the 2.6 us SET loss;
   shaving the template alone pays at most 0.47 us.
3. Atomics: 14 of the 25 PAN windows per request are `ldadd` in one helper, 22.6 ns per window in situ
   (0.32 us, 12% of L); the SIMD&FP windows cost 11.8 ns each (0.13 us). A faster path for the helper
   or for the outline-atomic call pays 0.3-0.45 us per request.
4. 0.6 us (SET) of mid-block native-equivalent instructions run slower than natively for a reason the
   counted units do not name; not SSBS (native insensitive), not LDTR latency (`chase`), not cold
   caches (`-P 16` equals non-pipelined). The counted overhead rows (budget, fills/spills/helpers,
   alignment checks) total only 0.42 us (SET) / 0.34 us (GET), which is what the micro-model got right.
5. The FP boundary entry (one runtime entry, about 0.1 us) and the bracket (0.11 us) cost about 0.2 us per
   request. Bracketing every run (variant B) would remove the entry but pay the bracket on the second
   syscall resume as well: no gain.
6. Native slack: the wall loss is 0.97 us (SET) / 1.02 us (GET) smaller than the server-CPU increase,
   because the native server idles 25%. The wall cannot follow the server time below what the loop
   delivers: with fragments refused the server needs 3.42 us per SET and the wall is 3.54 us.

### Not verified

- The sampler assigns time by the instruction at the head of the ROB with interrupt skid; it is calibrated
  on one loop (`calls`) only. Per-word figures are not exact; class and position totals are cross-checked
  against CNTVCT (1-3%).
- Why a dispatch jump stalls: the data fit an unpredicted/mispredicted indirect jump behind a
  three-load chain, but no PMU is visible in the HVF guest; an I-cache or BTB capacity cause is not excluded.
  `sites256` failed the run's own in-kernel check (return targets that are not fragment entries become
  fragments: 256 profile slots), so the capacity question was not answered.
- The mid-block row (0.6 us) has no explanation.
- Counts come from QEMU TCG with 50 clients, not from the guest: batching differs (native guest 2.31
  hook calls per request, KJIT 2.04, TCG about 2.0); the vDSO `clock_gettime` code (two fragments) is
  not in the trace; the ifunc choices (memcpy, strchr) are those of neoverse-n1 under QEMU and agree with
  the functions seen in the guest samples.
- One guest configuration (4 vCPUs, M1/HVF, single host with other agents' runs): the wall columns vary
  by about 4% between boots; `--threads 2` has 2 boots, the SSBS run 3.
- The no-publish and FP-refusal ablations change the program's native/fragment split, so their wall
  times are not component costs, except the per-entry figure (101 ns), which is a difference of two
  runs of the same code.
- The timers cost 0.25 / 0.36 us (A/B) and are inside F, R and the gaps; the sampler costs 7-10%.
