### Semantics

Faults (`exp_simd_fault`, EL0, 3 identical boots; two pages, the second PROT_NONE, access
crosses at byte k; LDTR/STTR are plain accesses at EL0 and fault the same way):

- Native on this CPU: a load that faults leaves the faulting register untouched and
  has already written every register it completed (`ldp q0,q1` with q1 faulting: v0
  changed 16 bytes; `ld1 {v0-v3.16b}`: 16-byte units); a store has written every whole
  16-byte register it completed and none of the faulting one (`str q` crossing at k = 8
  writes 0 bytes).
- C3, all pieces to scratch first: no V register is ever written at a fault (cleaner than
  native; the Mem exit re-executes natively, which redoes the load). Stores: memory is
  written in 8-byte units (`str q` at k = 8/12 wrote 8 bytes, `stp q` at k = 24 wrote 24).
  Native re-execution rewrites them with the same data; as for the GPR pair lowering (two
  STTR) A5 already accepts.
- C3 with one scratch (`c3s`): a half-loaded q register is visible (low half new, high
  half zero, the `fmov d` zeroes it): v0 changed 16 bytes at k = 8, `ldp` k = 24 changed v0
  and v1 where native changed v0. Harmless after native re-execution, but not "state before
  the instruction"; the differential oracle would see it at the exit.
- C0/C1/C2: the same instruction executes, so the footprint is native's.

Single-copy atomicity (Arm pseudocode, ISA_A64_xml_A_profile-2026-03
`shared_pseudocode.xml`, `aarch64/functions/memory/Mem`): a 16-byte SIMD&FP load/store that is
8-byte aligned is two 64-bit single-copy-atomic accesses, in any order, before the FEAT_LSE2
rule is consulted; a 32-byte `LDP`/`STP` (SIMD&FP) aligned to 8 is four 8-byte accesses (a
single 32-byte access only with FEAT_LS64WB and 32-byte alignment); `LD1` is per element;
`ldr d/s` is one access of that size. So 64-bit LDTR/STTR pieces keep the architectural
atomicity of every 8-byte-aligned q/d/s access. Not 8-aligned: the architecture promises
nothing but implementation-defined atomicity inside an aligned granule >= 16 bytes
(LSE2 `MemSingleGranule`), which C3 loses. Preconditions for C3: FEAT_LS64WB absent
(`ID_AA64ISAR1_EL1.LS64 < 4`, 0 here), pin it at module init like A7c pins LSE2.

Scratch (pool x12..x15): C3 loads, all-pieces-first: `ldr b/h/s/d` 1, `ldr q` 2, `ldp s/d` 2,
`ldp q` 4, `ld1` 1-2 registers 2-4 (plus a base fill: the last LDTR may overwrite the base
scratch if the base needs no writeback; plus the SP-check scratch shared with a data
scratch), `ld1` 3-4 registers 6-8: do not fit, stay Unsupported or take `c3s`. Stores need
1-2 whatever the register count. C0/C1/C2 keep today's 3-4. Code size per access:
C0 6-7 words, C1/C2 4 (+2 per window for C1), C3 2 (d/s), 4 (ldr q), 8 (ldp/stp q), 16
(4-register LD1/ST1). Coverage: C3 can lower every in-scope load/store, the register-offset
and literal forms (address into scratch first), LDNP/STNP, LD1R and lane forms, `dc zva`
(eight `sttr xzr`), and cannot lower LD2-LD4 (de-interleave) or anything needing a vector
temporary. C2 (privileged access) covers every form including LD2-LD4, because the original
instruction runs on a range-checked address.

### C2: what a safe version needs, and the run-scoped form

A region window inside a fragment (a loop across its back-edge) needs: a PAN-state
dataflow in the verifier (every word of the region known PAN-clear, joins from outside
rejected), a PAN-restoring variant of every exit that can be reached from inside (Mem
stubs, budget stub, template miss, the fall-out to the epilogue), the budget `cbz` inside the
region going to such a stub, the fault-site entries of LDTR/STTR and window accesses inside
naming PAN-restoring stubs, region entry/exit insertion at layout (natural-loop
detection), and no `BL`/`BLR`/`BR`/`RET` templates inside. Interrupts are fine at init's
`SCTLR_EL1.SPAN == 0`: exceptions enter with PAN set and `ERET` restores the clear PAN.
That is a large verifier and layout change for one window per loop.

The run-scoped form has none of that: the A13 bracket (`kjit_call_fragment_fpsimd`)
clears PAN with one `msr pan,#0` right before `kjit_call_fragment` and sets it right
after it returns. Every exit of a fragment run already funnels through the epilogue `ret`
to that one place (budget exit, `Mem`/fault stubs after the fixup, runtime exits); the
verifier only has to require the range check before each privileged access and forbid
`msr` altogether. Why it is no weaker: with PAN clear the verifier's rule 3 still limits
every plain load/store to the kernel frame, `pt_regs` and the dispatch table, so no
unverified instruction can touch user memory; PAN never protected kernel memory. A
kernel-mode loop with PAN = 0, interrupts and preemption enabled and no call in it
(`exp_simd_panirq`, 300 ms on cpu1 and cpu2 with a busy task on the same CPU): the loop
read PAN 2.3e8 times and never saw it set; 302/302 and 303/303 1 ms hrtimer interrupts hit
the PAN = 0 context, and in all of them the handler saw PAN = 1 (SPAN = 0) and the
interrupted SPSR had PAN = 0; 38 involuntary preemptions of the loop, PAN stayed clear
across them; no migration. The cost is the same per run, not per access: `msr pan,#0;#1`
4.1 ns, plus 3.0 if the code between them follows a branch.

### C4: features and kernel facts (`exp2ids`, boots F1-F3, M1/HVF guest)

FEAT_LSE2 (ID_AA64MMFR2.AT = 1) and LSE, LRCPC2, CRC32 present; PAN2 (MMFR1.PAN = 2), UAO
present, EPAN off, SPAN = 0, nAA = 0, A = 0; DCZID_EL0 = 4 (64 B block, DZP = 0); no
LSUI (ISAR3.LSUI = 0), no MOPS (ISAR2.MOPS = 0), no LS64 (ISAR1.LS64 = 0), no SSBS, MTE,
SVE, SME, BTI. The guest hides nothing that would help; FEAT_LSUI is the hardware fix
(`LDTP/STTP/LDTNP/STTNP Qt1,Qt2` are unprivileged SIMD&FP pairs in the 2026-03 XML; no
single-register q form) and FEAT_MOPS has unprivileged copy/set variants (`CPYFPWT*`,
`SETPT*`); neither exists on this host. `FEAT_UAO` goes the wrong way (makes LDTR
privileged). The register form of `msr PAN` is 5x slower than the immediate. Kernel
config: `ARM64_SW_TTBR0_PAN` off, `ARM64_EPAN` off, 48-bit VA, PREEMPT, no SVE/SME.

### Ranking and recommendation

Speed = geometric mean of the six loop slowdowns, plus the per-access cost; contract =
what A9/A8 promise today.

| rank | candidate | speed | contract kept | needs |
|---|---|---|---|---|
| 1 | C2 run-scoped (PAN cleared by the bracket) | 1.37x; 0.2 ns/access | all of A9 (the same instruction runs: footprint, atomicity, even LS64WB); defence in depth for plain accesses is given up (analysis above) | trampoline `msr pan`, verifier rule 8 shrinks, PAN windows and PAN stubs disappear from reg-virt/layout/rephrase |
| 2 | C3 | 2.32x; 0.2-0.86 ns/access | PAN invariant and every verifier rule; atomicity exact for 8-aligned (pseudocode), store footprint 8-byte granules, V state clean | new reg-virt lowering, scratch limits (LD1 3-4 regs), code x2-4, LS64WB init check |
| 3 | C1 | 14.2x; 1.0-5.0 ns/access | A9 shape | verifier window generalisation; still 9-24x on loops, window sits behind every back-edge |
| 4 | C0 today | 29.9x; 7.6 ns/access | A9 | none |

Recommendation: C2 run-scoped. It is the fastest, keeps the access instruction native
(no new atomicity or fault argument), covers every SIMD&FP memory form (LD2-4, register
offset, `dc zva` need no lowering other than the address), and the same change would
take LSE atomics out of windows (not measured here). Its price is one new kernel
invariant (PAN clear for a bracketed run). If that is refused, C3 is the fallback; do
not build C1 (14x) or loop-scoped C2. Cheap and useless alternatives: reordering today's

## 03:03 +0800 — Dispatch stall: cause and alternatives

Commit: d01231a (branch `exp/dispatch-study`, experiment-only, not merged)

Question: in redis the in-fragment dispatch costs about 5 ns per transfer where a one-site loop costs 0.4 ns
(2026-10-11 01:54). Which mechanism is it (mispredicted `br x12` behind the load chain, BTB/indirect-predictor
capacity, I-cache/iTLB footprint, something else), and which alternative removes it?

### Answer

- **Cause: fragment placement, not dispatch.** Every fragment image is its own page-aligned `execmem_alloc`, and a
  fixed 77-word (308 B) prologue/epilogue precedes the body, so the hot first lines of all fragments sit at the same
  page offset, on 8 KiB-spaced odd pages (VA[12] = 1; 15 of 18 images of `sites16` are on one VA[14:12] colour). On
  this core's L1I (192 KB, 6 ways, set index VA[14:6]: 8 page colours) a cyclic walk over more than 6 x colours such
  blocks misses on every block entry. Measured capacities: 48 / 24 / 12 / 6 blocks at strides of 4 / 8 / 16 / 32
  KiB, exactly 6 x (32 KiB / stride), at EL1, EL0 and on the host. Redis has ~300 hot fragments (296 live, 2026-10-11
  01:54), so nearly every call target, return target and in-fragment branch target is an L1I miss (about 3.5-4 ns
  each in the kernels, ~5 ns in redis). The invariant that broke is not in the contract: "hot fragment code does not
  collide in the instruction cache" was never stated, and a page-per-fragment allocator violates it.
- **Evidence that separates it from the other candidates** (details in section 1): the same redis binary, the same
  lowering, the same template, only the start offset of each image changed (module parameter, 10 lines) takes SET
  server CPU from 6.42 to 3.92 us per request with 16 colours and 3.58 us with fragments packed densely (native 2.67),
  and the SET throughput from 0.586 of native to 0.96 (16 colours) .. 1.02 (packed); the load-chain length (1/2/3 loads), `b` against `br x12`,
  and `ret x12` against `br x12` change nothing while the stall is there; the *native* `bl`/`ret` code laid out the same way
  is 13x slower; the number of sites (1..256) and the 3x code footprint cost nothing when the placement is
  dense.
- **Alternatives:** the placement fix (D6) is the only change that matters (SET -2.8 us per request of server CPU).
  With placement fixed, the dispatch template costs 0.64 ns per transfer when its 31 extra instructions per call+return
  are exposed (throughput-bound code) and nothing when the code is latency-bound: at most 0.155 us per SET request.
  D1-D5 recover at most 0.07 us of that (D2, D3, D2+D5), D4 is 0 to +0.02 us, and each needs contract changes
  (section 3). Recommendation: do D6 (pack, or colour as a stop-gap) and leave the lowering alone (section 4).

### Method

- `tests/guest/exp_disp/gen.h`: a portable run-time A64 emitter. A *program* is a call DAG with work between calls
  (`fn`, `w`/`v` work, `c` direct call, `p` call through a PLT stub, `i` pattern-driven indirect call, `r` random
  branch, loops); a *lowering* turns it into native `bl`/`blr`/`ret` (the native twin) or the A11 form: budget check,
  target into x13, link write, the 20-word template (word for word the real one apart from its four imm19 fields,
  checked against `frag-dump`, a harness bin that prints the real fragment of any raw code). Options: template shape (`real`, main probe
  only, 16-byte slots `d4`, 0..3-load chains), final branch (`br`, `blr`, `b`, `ret x12`), call lowering (template,
  direct `b`, direct `bl`, inline cache of K targets), return lowering (template, K compares), budget on/off.
  *Placement* reproduces the fragment layout: every function entry and every call continuation is a block at a
  multiple of `frag` bytes plus `foff` (+ `fstep` per block, mod `fmod`), followed by the dead exit group; the real
  KJIT is `frag=8192 foff=308`. The same generator runs in an EL1 module (`mod.c`, debugfs `expd/run`; code in
  `execmem_alloc` memory like a fragment, `set_memory_rox`, IRQs off), in a static EL0 driver (`user.c`, the EL0
  twin in the guest) and on the macOS host (same binary source, MAP_JIT; cycles and instructions from
  `proc_pid_rusage`, the only PMU view available without root).
- Kernels: `sites` (N call sites of one leaf, N return targets), `sitesd` (N leaves), `poly` (8 indirect call

### 3. What each alternative needs from the contract and the verifier

| | contract / verifier (rules of section 6) | budget unit | patching, retire/unlink | risks |
|---|---|---|---|---|
| D0 | the current template | 1 per transfer | none; retire = clear slots | the placement of its fragments |

### 4. Recommendation

1. **Fix the placement (D6).** Packing is the end state (redis SET server CPU 3.58 us, GET 3.44; latency-bound
   kernel at native speed in the real module). Colouring with >= 16 colours is the cheap stop-gap (3.92 / 3.67, 10 lines,
   no verifier change, up to one page more per fragment). Either needs a regression guard: a test or debugfs counter
   that bins the start offsets of installed fragments, since a layout bug of this kind is invisible to every functional test.
2. **Do not change the dispatch lowering for speed now.** After the fix the template is <= 0.155 us per SET request
   (bound) and the best alternative returns 0.07 us of it, below the redis noise (+-2%); the contract cost
   (CFG through calls, multi-range invalidation, x30 virtualization, link patching or retranslation) is larger than the
   gain. D4 should not be built at all. If a dispatch change is wanted after the next attribution, D2 + D5 is the only candidate
   with an effect (-44% of the lowering cost in throughput-bound code, 0.98 against 0.65 ns per pair native).
3. Re-run the 01:54 attribution on the packed build: the dispatch and mid-block rows should disappear, and the
   0.9 us that remains is PAN windows, runtime entries, budget and reg-virt in the order of that table.
4. `docs/pipeline.md` is out of scope here: when D6 lands, its contract line (hot fragment code must not map to the same
   instruction-cache sets) belongs in section 8 next to the fragment allocation.

### 7. What is left: the front end, not the memory model

## 16:21 +0800 — Redis under UB's benchmark protocol

Commit: the commit that adds this entry (branch `exp/ub-standard`, worktree `.claude/worktrees/ubstd`, base c97a98d; tooling only, no module,

Question: the Userspace Bypass paper (OSDI '23, section 6.2; `tmp/UserspaceBypass/Readme.md`, "Redis test") reports redis
GET +4.4..10.8% throughput with its boost, in a VM with KPTI on. What does KJIT (A14) do under the same benchmark
protocol, with KPTI off and forced on, and where does it stand against UB and against the ceiling set by the
syscall round trip?

### UB's protocol, and our adaptation (deviations marked D)

UB: redis 6.2.6, server and client on two machines joined by a NIC, `redis-benchmark -t get -n 1000000 -d <size>
--threads 2`, `-d` from 2^0 to 2^14, every GET test preceded by a SET test with the same `-d`, boost on `write` only,
20-30 s of load before the boost took effect.

Ours: kjit-guest, 4 vCPUs (M1, HVF), server and client in the one guest over loopback. Per `-d` in 1, 2, ..., 16384:
SET then GET, each `redis-benchmark -t <set|get> -n 1000000 -d <size> --threads 2 -q`, everything else default
(50 clients, no pipelining, one key); KJIT off, then KJIT on; one run per cell per boot. Off = `kjit.ko` loaded,
debugfs `enable=0 auto=0`; on = `enable=1 auto=1 chain_budget=1024`. Pinned: server (all its threads) on CPU 0 by
`taskset -a -pc`, client on CPUs 1-3. Unpinned (one size, `-d 4`): nothing pinned. Per boot: `ub-bench.sh sys 7` (null
syscall), the pinned sweep, the unpinned point. 5 boots per KPTI setting, order k0 k1 k0 k1 ..., every boot through
`host/ub-run.sh` (all waited 0 s; load1 before the boots 2.8-5.9, after up to 7.1), `UB_APPEND_EXTRA=rodata=off` for both
settings, KPTI-on boots confirmed by the kernel line "kernel page table isolation forced ON" (the driver checks it).
Warm-up: once at the start of the invocation, SET and GET at KJIT on with 1M requests; per size, before the measured runs,
SET and GET at 200000 requests in each state (not recorded). Server CPU per request = (utime + stime ticks of the server
from `/proc/PID/stat` over the run) / requests (CONFIG_HZ=250, USER_HZ=100 ticks; the total equals the scheduler's exact
runtime to a tick, the user/system split is tick-sampled). KJIT counters are debugfs deltas per run (the client runs
under `nojit`, so they are the server's).

Deviations:

- D1. redis 7.0.15 (the guest's; UB 6.2.6).
- D2. One guest on loopback, no NIC and no second machine; the client shares the guest kernel and the 4 vCPUs. Pinning
  approximates two machines only in CPU time, not in kernel/network-stack work (the loopback receive path of the
  client's packets runs on the sender's CPU).
- D3. The client runs under `nojit` (allow-all seccomp), so its syscalls pay the seccomp filter; the same in both states.
- D4. `-q` (quiet output). Output format only.
- D5. KJIT translates all hot redis code around every syscall (auto mode), not only `write`. All syscall classes are
  included in "syscalls per request".
- D6. "Off" has the hook and module loaded (null syscall +11..15 ns, 21:41 entry), not an unpatched kernel. The module
  is loaded with defaults and switched by debugfs, as the other `ub-*` scripts do, not by module parameters.
- D7. KPTI forced on aarch64 (`kpti=1`; the M1 reports "Not affected"), not x86 KPTI; both settings with `rodata=off`.
- D8. Order within a boot is always off then on; no alternation.
- D9. Unpinned: one size point only, `-d 4`.
- D10. Warm-up is 1M + 2x(200k) requests per size, not 20-30 s of continuous load; its sufficiency is the settled
  check below.
- D11. Throughput is `redis-benchmark`'s own number. With `--threads` it detects completion in a 250 ms timer, so
  every run time (and every req/s) is quantized in 250 ms steps (3.00 s -> 333333, 2.75 s -> 363504, ...: 8% at
  3 s). The quartile columns of throughput are therefore coarse; the exact quantity is server CPU per request. The
  server was busy 0.90-0.99 of the wall time in both states, i.e. it is the bottleneck, so 1/CPU is the throughput
  without the quantization (CPU on/off 1.6 against throughput on/off 0.65 at `-d 1`, consistent).

  counting only native minus in-kernel. Against the server CPU of off (2.6-3.0 us at small sizes) that is a ceiling gain
  of +10..11.6% / +16..18% (full) or +5.4..6.1% / +11..12% (achievable) at `-d <= 128`, falling to +6.5% / +10% (full)
  at 16 KiB because the request is longer. UB's +4.4..10.8% sits inside this band; ours measured -24..-72%. The loss is
  the 1.1-1.6 us per request of fragment execution and runtime entries (see 12:42, attribution on A14: PAN windows,
  dispatch, runtime entries), 4-11x the saving.
- **KPTI helps, but nowhere near enough.** Forcing KPTI on raises the native round trip by 75 ns, the off-server CPU by
  0.2-0.3 us, and lifts on/off throughput by about 0.07 at the small sizes (GET 0.65-0.67 -> 0.72-0.75 at `-d 1-4`); the
  sign does not change. Same finding as 21:41, now over the UB sweep.
- **Size trend.** The value size hurts KJIT more than native: on/off falls from 0.65-0.75 at 1-32 B to 0.28-0.30 at 16 KiB,
  CPU on-off grows from +1.5 us to +11 us. The off side grows by 1.4 us over the same range (2.7 -> 4.2). This matches
  the 09:05 inference (q-register copies cost a PAN window per access in fragments), not measured here.
- **Where UB could still be reached.** Not by this tree. If the fragment code and the entries cost nothing, the
  achievable gain would be +5..6% (KPTI off) and +11..12% (KPTI on) at small sizes, which reproduces UB's range, and
  nothing more: the syscall transition is 6-15% of the request on this platform.

### Settled translation

Over 320 measured KJIT-on runs, `translate_ok` grew in 18 (107 translations in total, 94% of the runs 0): +1 or +2 in 15
of them, at `-d 16384` GET +8, +14 and +69 (k0-b3, k1-b5, k1-b3). `-d 16384` GET keeps finding new code, the other sizes are settled after the warm-up. KJIT-off runs with a fragment
entry: 0. No `exit_invalid`, verifier rejection or bad word in any run (the script fails otherwise).

### Not verified

- UB's absolute numbers and their environment (x86, NIC, redis 6.2.6, `write`-only boost); nothing here was run there.
- Throughput resolution (D11): the medians are of values quantized in 8% steps; the CPU-per-request columns are the
  precise ones. A repeat with 10M requests, or an outside observer of the last reply, would resolve the throughput.
- The user/system split of the ticks was not used. The CPU gap here (+1.5 us SET at `-d 1`, KPTI off) is larger than the
  1.0 us of the 12:42 entry (module-timed, default benchmark arguments, paired); the 12:42 tick-based boots on main gave
  +1.84 / +1.14 us, so the difference is probably the method or `--threads 2`, not investigated.
- Syscalls per request are taken from the hook count of the KJIT-on runs; off has no hook counter (assumed equal).
- Why the large sizes cost more (the 09:05 PAN-window hypothesis) and the unpinned point beyond `-d 4`.
- `kjit-guest-debug` profile, other redis commands, `-P`, `-c`.
- The load on the host: 2.8-7.1 (other agents' guests were not running: `ub-run.sh` waited 0 s every time, but the host
  has other processes).
