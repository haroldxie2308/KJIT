## 00:04 +0800 — Worktree tooling fixes

Commit: 9c4bd89

Four tooling bugs hit while running A11 from git worktrees, each reproduced and
fixed at its cause (agent report, audited):

- `scripts/docker-dev.sh`: a worktree's `.git` file points at
  `<main>/.git/worktrees/<name>`, outside the `/workspace` mount, so every git
  call in the container failed (exit 128). Fix: mount the git common dir at its
  host path. Verified from a worktree and (by me) from the main checkout.
- `scripts/guest-run.sh`: the QMP socket under a deep build root exceeded the
  104-byte unix socket path limit on macOS. Fix: a private `mktemp -d` socket
  dir per run; `require_unix_socket_path` fails fast on any path still too
  long. Verified: `make guest-run` from a worktree without a symlink.
- `make guest-run CMD=...`: `$(CMD)` was pasted into the recipe, so double
  quotes broke it; now `$$CMD`. Remaining limit: make still expands `$` on its
  command line (write `$$` or pass CMD through the environment).
- `scripts/mk-guest-rootfs.sh`: Docker Desktop resolved a scratch dir that was
  deleted and recreated at the same path to the deleted one (`/out/<test>: No
  such file`, 3 of 8 back-to-back runs; a 30-iteration mount experiment failed
  24/30 with path reuse, 0/30 with fresh paths). Fix: a fresh `mktemp -d` work
  dir per run. Verified: 15/15 back-to-back `guest-rootfs`, 8/8
  `guest-rootfs` + `guest-run`.
- Not run after the cherry-pick onto A11: the guest suites (scripts only).

## 00:47 +0800 — Dispatch-table miss classification

Commit: ef6f971

Question: after A11 every `ibtc_insert` was an `ibtc_replace` under
redis-benchmark. Are the BL/BLR/BR/RET exits that still reach the runtime
cold misses, conflict misses (direct-mapped aliasing) or something else; are
conflicts concentrated (aliasing) or spread (capacity); call targets or return
sites?

Method: the runtime classifies each branch exit against the run's own table
slot before publishing (`runtime/ibtc.rs`): cold (empty), conflict (another
pc's record), other (same pc, only through a racing publish); non-FP -> FP
exits (`ibtc_fpsimd_boundary`) are excluded. Per-slot conflict counts per table
class with the last evicting/evicted pc in debugfs `ibtc_slots` (`reset` zeroes
them). `tests/guest/a11-baseline.sh` resets/dumps them per run and prints the
server's `/proc/<pid>/maps`; pcs mapped to symbols with `llvm-nm` on the
binaries from the rootfs. Points `off` and `chain_budget` 1024, 3 passes of
`-t set` and `-t get` x 200000 requests, fresh server per boot, 2 boots
(orders `off 1024`, `1024 off`), kjit-guest, M1/HVF, 4 vCPUs, host load ~4-5.

Commands: `./scripts/docker-dev.sh --no-tty -- make module-build
KJIT_KERNEL_PROFILE=kjit-guest`; `make guest-rootfs`; `./scripts/guest-run.sh
--profile kjit-guest --run-dir <runs>/a38-miss-boot{1,2} --timeout 2400 --
'set -- /tmp/a11 3 200000 off 1024; . /opt/kjit-tests/a11-baseline.sh'`.
Gates: `make guest-tests`, `make guest-tests-k3` ALL PASS.

Raw data: serial logs `runs/a38-miss-boot1`, `a38-miss-boot2`, `a38-ab` under
the build root of worktree agent-ac3b24e86f29900e2; copies and analysis
scripts in the session scratchpad (not kept in the repo).
Data: [docs/data/2026-10-09/0047-dispatch-miss-classification.csv](../data/2026-10-09/0047-dispatch-miss-classification.csv)

Results (per request, chain_budget 1024, mean of 6 runs; identity
cold + conflict + other + boundary == branch exits held in all 24 runs):

| test | req/s | runtime entries | cold | conflict | other | FP/SIMD boundary |
|---|---|---|---|---|---|---|
| SET | 115953 (100251..130124) | 28.51 | 0.018 | 18.49 | 0 | 7.98 |
| GET | 136615 (121803..154202) | 15.93 | 0.004 | 8.83 | 0 | 5.05 |

KJIT off: SET 223783, GET 223459 req/s (mean of 6). Conflicts sit in 5-17
slots per table; the top 8 slots hold 94-100%. Nearly every hot slot is a
two-pc ping-pong between redis functions 16 KiB apart, e.g.
`processCommand+0xfc` (return site) / `string2ll`, `counts_index_for+0x14` /
`keyIsExpired`, `zmalloc` / `call`, `je_malloc` / `dbOverwrite`. Function
entries and return sites both appear (SET: ~10.2 vs ~8.4 conflicts per
request).

Conclusion: beyond the by-design FP/SIMD boundary, misses are almost entirely
conflict misses from a handful of aliasing pairs; capacity and cold misses are
negligible. The table is not too small but direct-mapped on `pc[13:2]`.
Removing the conflicts would leave about 10 runtime entries per SET request
and 7 per GET (inferred, not measured).

Caveats: no hit counter (no hit rate); per-slot counters are global across
mms; libc symbols are dynsym-approximate; debug profile not run; host varied
~15% between boots; the instrumentation's own cost was not resolvable
(A/B medians -2.2% SET, -0.1% GET within +-15% noise).

## 00:56 +0800 — FP/SIMD bracket: core problem and the experiments launched

Commit: none (discussion; experiments in progress)

- Core problem: fragments use the user's V0-V31/FPCR/FPSR live in hardware.
  arm64 Linux saves them lazily (only at context switch or kernel-mode NEON,
  restored on return to userspace), so the registers are guaranteed to be the
  task's only while preemption and softirqs are off: hence the
  `local_bh_disable` bracket, and `pagefault_disable` because it is atomic.
  Before A11 the bracket ended at the FP/SIMD fragment's first exit; since A11
  a bracketed run dispatches through `table_all` into integer code, so the
  non-preemptible stretch is a whole run (see 2026-10-05, review finding).
  Cutting it per fragment instead costs ~8 runtime entries per SET request
  (the `ibtc_fpsimd_boundary`).
- Hypothesis under test: this kernel's task-level `kernel_neon_begin(state)`
  (TIF_KERNEL_FPSTATE, state saved/restored at context switch) allows a
  preemptible bracket: load the user state into the registers, run, store it
  back. Experiment (prototype, variants A = latency only, B = one table)
  delegated; pagefault_disable kept in v1 to avoid nested task-level NEON in
  fault paths.
- Dispatch-table conflicts: three variants (index hash, 2-way sets, victim
  table) delegated as a measured prototype experiment.

  (the boundary falls from 7.9 to 1.0 per SET request: runs now stay longer in
  the bracket once entered).
- V1 depends on ASLR (4.1-13.9 conflicts/req over 6 boots); 16-byte-aligned

  processCommand+0xfc, call, string2ll) in 2 ways.
- Miss-classification overhead (V0, n=12 each): SET 102.0k vs 103.0k without it
  (< 1%).

Conclusion: V3a (+2 KiB per table, main-slot hit identical to V0) and V2b

#### Q3. Cost per covered syscall

KJIT, measured: a dispatched call/return costs 2.5 ns per transfer in a hot
loop (`entry_cost`, 2026-10-05); redis at `chain_budget` 1024 runs 1.93x
(SET) / 1.61x (GET) slower than off after A11, 0.61 / 0.68 with the victim
part (2026-10-09 03:56), floor 3.04 runtime entries per request; per Step 0
transfer the remaining loss is 11.5 ns (SET) / 8.8 ns (GET) net of the saved
syscalls, i.e. 12.2 / 9.6 ns gross (my arithmetic: (4.04 + 2 x 0.12) / 352 and
(2.64 + 2 x 0.12) / 299 us), with 50-80% of the loss inside fragment code
(budget read-modify-write through memory, stack-backed x12-x15, `LDTR` imm9
splits, PAN windows), not timed per phase (2026-10-05).

UB, static counts only (four shipped regions; no timing, no run): translated
instructions are 1.97-2.09x the originals; `shl/shr` mask pairs are 6.8-12.6%
of original instructions, i.e. 13-30% of the memory-access instructions;
register-conflict spills to `Stack_*` slots touch 22-29% of original
instructions; a call is 4 instructions, no budget, no table; a return is
`pop` + a chain of 3 instructions per known target (mean chain 0.2-1.3). The
dynamic slowdown of that code is not derivable from this (ESTIMATE only:
independent extra instructions on an out-of-order core, so well under 2x
time).

Which is cheaper per instruction and per transfer: per transfer UB is cheaper
(about 4-8 instructions, no budget, no memory-resident table) than KJIT's
about 18-20 words, 2.5 ns (hit) and 12 ns (redis, gross). Per instruction both
roughly double the instruction count; KJIT additionally turns every user
load/store into a split `LDTR`/`STTR` plus reg-virt fills and pays a budget
read-modify-write, UB's mask is only on some accesses (Q4). The cheap UB
transfer comes with the missing guarantees (no time bound, learned-only
targets, linear return chains).

Break-even (ESTIMATE, assumes cost linear in transfers and a 120 ns saving):
a covered gap wins only if its transfer count times the per-transfer cost is
under 120 ns, i.e. at most 48 transfers at the hot-loop 2.5 ns and 10-12 at the
redis-observed 10-12 ns. Redis gaps have 23, 45, 48, 255 and 291. At the
hot-loop price only the three short pairs break even; at today's observed
price none does. This is why KJIT, which covers the long pairs, loses
throughput while a UB-style short-gap filter would be roughly neutral.

#### Q5. Adoptable ideas

1. Gap-length filter in the K3 profiler (UB `stat.c:8,56-68`). Take the
   measured user time between a syscall's end of the previous run and the next
   syscall's entry, and only queue a translation for a resume PC whose gaps are
   short. Cost: policy only in `docs/pipeline.md` section 9, plus a timestamp
   at syscall entry (patch 0001 currently hooks only after the syscall, and the
   duration of a blocking read would pollute a post-hoc gap): one `CNTVCT` read
   and a store per syscall on every kjit-registered task. Breaks no ABI,
   verifier or fragment contract. Expected effect (ESTIMATE): redis keeps
   fragments at write and epoll_pwait resumes only (about 57% of syscalls,
   12% of user instructions), the 1.6-1.9x slowdown disappears (the long pairs
   run natively) and the best case is about +3% (half the 5.7% bound), not a
   large gain. The decision it forces: is the project's success measure
   "syscalls in the kernel" or throughput, since the two now disagree.
2. Payoff-based disablement (UB `exe.c:103-114` tracks success vs fail per
   region). Negative-cache a PC whose runtime entries per in-kernel syscall
   exceed a bound (counters exist: `chain_hist`, per-exit counts). Policy
   only, section 9 negative cache; changes nothing in the verifier. Cheaper
   and more general than idea 1 because it uses KJIT's own cost signal, but
   it needs per-PC counters in the hot hook path.
3. Direct in-fragment calls (UB `special_inst.py:33-37`: a call whose callee
   is in the region is a plain jump). Lower a `BL` whose target is in the same
   fragment to link write + `b`, keep `RET` on the table. Saves about 2 ns of
   the 2.5 ns for roughly 42% of transfers (121 of 291 per long gap): about
   0.26 us of a 4.0 us request loss, ~6% of the loss (ESTIMATE). Cost: CFG
   must follow `BL` (pipeline pass 3), callee text duplicated per fragment (16-page
   translation limit, wider invalidation spans), rule 6 must still charge
   backward/recursive calls. Not worth it before in-fragment code quality,
   which holds 50-80% of the loss.
4. Cheaper entry/exit (UB wrapper loads and stores only what it uses plus
   saves 6 callee-saved registers). Writing back fewer than 31 GPRs per `Svc`
   would break the ABI contract (epilogue writes the full state, byte-exact in
   rule 2) and anything that reads `pt_regs` wholesale (clone, signal frames);
   needs a syscall allow-list. Not recommended.
5. Not adoptable: offline Python recompile loop and the whitelist, per-thread
   regions, learning by miss-then-disable, kallsyms in the fault path, direct
   `sys_call_table` calls, no budget. Each trades a KJIT guarantee for nothing.

### Verdict

UB and KJIT share the core idea (kernel-mode execution of a snapshot of user
code, chained across syscalls through `pt_regs`) and differ in what they
promise. UB is a performance prototype: short paths, learned control flow,
cheap transfers, and, in the released code, almost no safety machinery (partial
masks, a stub fault path, no budget, no verification, no syscall-work check).
KJIT is a semantics-first system: exact faults, a bounded run, a verifier, and
all transfers inside translated code at a measured cost.

Advantages of UB for this goal: cheaper control transfers, small regions, and
above all the short-gap selection, which is a cost/benefit rule that fits a
platform where the saved transition is cheap. Disadvantages: not an exact-
semantics design on AArch64-class guarantees, and an offline translator.

Advantages of KJIT: all of the safety and exactness the project states as its
goal, online learning with no stall, per-mm sharing, bounded time. Disadvantage:
it translates regions where its own per-transfer cost exceeds the saving, so
on this platform it is slower than native (1.6-1.9x) while hitting the highest
"syscalls in the kernel" figure.

Recommendation (disagree once, decide yourself): keep KJIT's contracts; adopt
idea 1 or 2 as K3 policy before more work on fragment speed, because by the
numbers above the ceiling for redis on this M1/HVF platform is ~6% even at
zero translated-code cost and only short gaps can approach break-even. If the
project's success measure is throughput on arm64 without KPTI, the honest
expectation is "neutral to a few percent"; the larger lever is a platform with
costlier transitions (an affected core with KPTI), not the translator.

KJIT today (A11, direct-mapped table, no A11c) runs redis-benchmark at about

small here (M1/HVF guest, no KPTI). H2: translated code is itself slow and that,
not the remaining runtime entries, dominates the loss. H3: with expensive

### Model of one request (no KPTI; us)

Native CPU = U (user) + S (system); KJIT on = K (kernel work) + U x slowdown
+ in-kernel syscall overhead + runtime entries. Inputs: U, S above;
2.044 syscalls per request; 130.6 ns per native syscall round trip, 60.8 ns in
kernel; runtime entries beyond the `svc` resumes (SET 18.5 integer + 7.9
FP/SIMD, GET 8.7 + 5.0) priced at Step 0's 17.5 / 66 ns (low) or at 41-48 ns per
entry (its redis-measured slope, high).

| | SET | GET |
|---|---|---|
| native CPU (U + S) | 3.51 | 3.36 |
| KJIT-on CPU | 8.81 | 7.23 |
| added | +5.30 | +3.87 |
| transitions saved (2.044 x 70 ns) | -0.14 | -0.14 |
| extra runtime entries | +0.85 .. +1.27 | +0.49 .. +0.66 |
| fragment code slower than native (remainder) | +4.17 .. +4.59 | +3.35 .. +3.52 |
| => fragment user time / native U | 5.4 .. 5.8x | 4.8 .. 5.0x |
| share of the gross added cost: code / entries | 77-84% / 16-23% | 84-88% / 12-16% |

### Conclusion

- H1 supported. A native round trip is 131 ns (no KPTI), in kernel 61 ns; a
  request makes 2.04 syscalls, so the whole saving is 0.14 us of 3.4-3.5 us
  (4%); with KPTI 0.30 us (8%). The micro-benchmark gets 1.8-2.0x (no KPTI) /
  2.6-3.0x (KPTI) because it does nothing else.
- H2 supported. Fragment code runs 1.2-6.8x slower than native (34x for q-register
  copies), 4.1-4.3x with calls; the model puts 77-88% of the added cost per
  request in fragment code and 12-23% in the remaining runtime entries
  (5.4-5.8x / 4.8-5.0x fragment user time vs native for SET / GET). An
  A11c that removes all conflict misses (entries 28 -> ~3 per SET) can recover
  at most ~0.85-1.3 us of the 5.3 us (SET).
- H3 partly. Micro-benchmark: yes, markedly (speedup 1.8-2.0 -> 2.6-3.0).
  Redis: the on/off ratio rises 0.54 -> 0.62 (SET), 0.64 -> 0.76 (GET) at 3 B,
  0.44 -> 0.49 and 0.52 -> 0.59 at 4 KiB, because KJIT off gets slower; KJIT on
  does not change; the sign does not flip, and the server's CPU rises only
  0.15-0.24 us per request with KPTI (the slowdown of "off" is mostly the
  client's, which KJIT does not touch).
- Inferences, not measured: the 2 ns per tight-loop back-edge (strlen,
  copy: 2.2 ns per iteration against 0.2-0.4) looks like the budget counter's
  read-modify-write through memory (store-to-load forwarding latency on the
  loop-carried path); the 34x of q-register copies is the PAN window and range
  check per access (16 ns per 32 bytes), which also explains `-d 4096` (SET
  +3.2 us over 3 B on, +0.5 us off, ~1.6 copies of 4 KiB at 2 us each). Both
  point at fragment code, not at runtime entries.
