## 09:05 +0800 — Why translated fragment code is slower than native: root cause

Commit: a518d03 (branch `exp/frag-speed`, experiment-only, not merged)

Question: `code_speed` (journal 2026-10-09, "Why KJIT does not reach Userspace
Bypass's speedups") measures fragment code 2.2x-34x slower than native. Which
emitted instructions cost the time, per symptom? Hypotheses to confirm or refute:
PAN windows are expensive for q copies; calls pay budget + dispatch template +
target materialization; back-edges pay the budget read-modify-write (RMW)
through memory; byte loops pay LDTR splitting and reg-virt fills/spills.

### 1. Emitted sequences (hot loop, per original instruction -> emitted)

Roles: U user op (LDTR/STTR), W PAN toggle, R range check, B budget, D dispatch,
A align check, F fill/spill.

- strlen `ldrb w6,[x3],#1 ; cbnz w6` (2 insns) -> `ldtrb w6,[x3]` U, `add x3,x3,#1`,
  `ldr x12,[sp,#192] ; sub x12,x12,#1 ; str x12,[sp,#192] ; cbz x12,<stub>` B,
  `cbnz w6` = 7 insns.
- hash (5) -> 10 (ldtrb+add, 3 ALU, subs, B x4, b.ne). copy (4) -> 10 (ldtrb+add,
  sttrb+add, subs, B x4, b.ne).
- copy16 `ldp/stp x` + subs + b.ne (4 per 16 B) -> 15: `ldtr x13`, `ldtr x12`,
  `mov x6,x13`, `add`, `str x12,[sp,#24]` F, `ldr x12,[sp,#24]` F (the program
  uses x13, stack-backed), `sttr`, `sttr`, `add`, subs, B x4, b.ne.
- simd32 `ldp q0,q1,[x3],#32 ; stp q0,q1,[x7],#32 ; subs ; b.ne` (4 per 32 B) -> 20:
  per access `mov x12,x3 ; ubfx x13,x12,#48,#8 ; cbnz x13 ; msr pan,#0 ; ldp q0,q1,[x12] ;

- calls (14 insns per call+return) -> 64: caller `mov x0,x5` (1), B x4, target
  `movz/movk x13` x4 D, link `movz/movk x30` x4, template main-probe hit path 9
  (`ldr x12,[sp,#200] ; ubfx ; ldr ; cbz ; ldr ; sub ; cbnz ; ldr ; br x12`) D; callee
  fragment 21 (3 align pairs `and x12,x17,#15 ; cbnz`, 2 sttr, 1 sttr, 2 ldtr + 1
  ldtr, ALU) + B x4 + `mov x13,x30` + template 9; caller after the resume:
  `mov x5,x0 ; subs ; B x4 ; b.ne`. Three budget units per call iteration (bl, ret,
  back-edge) = 12 of the 64 instructions, all on one memory slot.

### 3. Per symptom (EL1 microbench vs fragment; ns per unit)

| symptom | native | + LDTR/add/etc | + budget RMW (= model) | fragment | residual |
|---|---|---|---|---|---|
| strlen (per byte) | 0.324 | 0.323 (`ldtrb`) | 2.129 | 2.14 | +0.5% |
| copy (per byte) | 0.319 | 0.319 | 2.087 | 2.10 | +0.6% |
| hash (per byte) | 0.946 | 0.947 | 2.218 | 2.14 | -3.5% |
| copy16 (per 16 B) | 0.376 | 0.536 (the x13 spill) | 2.083 | 2.11 | +1.3% |
| calls (per call) | 1.582 | 1.575 (ldtr, align, reg budget, bl/ret) | 6.247 (with dispatch template: 2.283 + 3.96) | 6.33 | +1.3% |
| simd32 (per 32 B) | 0.396 | 0.553 (range checks + moves) | 15.26 (15.35 without budget) | 15.44 | +1.2% |

- Byte/pair loops (strlen, copy, hash, copy16): the loop is one budget unit per
  trip; `strlen_rmw` 2.129 vs `strlen_reg` 0.320 (register counter) vs
  `strlen_ldtr` 0.323. Root cause: the budget counter's store-to-load chain through
  `[sp,#192]` costs 2.1 ns per unit at EL1, which exceeds the loop's own 0.3-0.95 ns.
  LDTR cost nothing (hypothesis refuted); fills/spills cost 0.16 ns/trip in
  copy16 only (x13 stack-backed).
- Calls: three units per call+return on one slot = 3 x 2.08 = 6.25 =
  `calls_bud_only` (native code + the three budget units): 6.407. Removing only
  the budget: 2.051 (`calls_nobud`); register counter: 2.283. Dispatch template
  with the register budget costs +0.71 ns per call (2.283 vs 1.575 with bl/ret);
  LDTR + align checks cost 0 (1.575 vs native 1.582). calls2 (5 units): 5 x 2.07
  = 10.4 vs fragment 10.55. Hypothesis "dispatch template + target materialization
  dominate": refuted, they are 0.71 of 6.25.
- simd32: one `msr pan` costs 2.07 ns (pair 4.13); a window around one access
  7.66 (the access cannot overlap the surrounding PSTATE writes: +3.5); two
  windows 15.3; the budget (2.1) hides under them (win1 15.26 with, 15.35 without).
  One window around both accesses: 7.68. Range checks and moves alone: 0.553.
  Root cause: PAN is switched with `msr` per access and each window costs about 7.5 ns.

One-sentence root causes: (1) tight loops, calls: the budget counter RMW on one
frame slot forms a loop-carried memory dependence of about 2.1 ns per budget unit
at EL1 (3 units per call = 6.3 ns, 1 per loop trip = 2.1 ns); (2) q copies: two
serializing `msr pan` per access, about 7.5 ns per window.

## 09:41 +0800 — The EL1 RMW-chain cost is PSTATE.SSBS = 0 at EL1 (speculative store bypass mode)

Commit: e926d1d (branch `exp/frag-speed`, experiment-only, not merged)

Question: the earlier entry left unexplained why a loop-carried memory RMW (the
budget counter) costs ~6.7 cycles at EL1 and ~1 cycle at EL0. Hypothesis: arm64
Linux runs EL1 with the Spectre-v4 mitigation (PSTATE.SSBS clear /
ARCH_WORKAROUND_2), which stops younger loads executing ahead of older stores to
the same address.

Verdict: confirmed for the mechanism (PSTATE.SSBS = 0 at EL1), refuted for the
assumed route (neither the Linux mitigation nor a firmware workaround is active,
and the command-line switches change nothing).

### 1. Facts (kjit-guest, M1/HVF; ub-facts1, ub-facts2, ub-ssbDef*, ub-ssbOff*)

- `/sys/devices/system/cpu/vulnerabilities/spec_store_bypass`: `Vulnerable`
  (default and with `mitigations=off ssbd=force-off`). Boot log: `CPU features:
  detected: Spectre-v4`; no SSBS line, no ARCH_WORKAROUND_2 / SSBD line; with the
  switch: `spectre-v4 mitigation disabled by command-line option`.
- `/proc/cpuinfo` Features has no `ssbs`. Read in the kernel (`exp_bench ids`):
  MIDR `0x610f0000`, `ID_AA64PFR1_EL1 = 0x0` (SSBS field 0), `SCTLR_EL1 =
  0xfc74799d` (bit 44, DSSBS, clear). `CONFIG_ARM64_ERRATUM_3194386` is not set.
  So the guest is shown a CPU without FEAT_SSBS (the hypervisor masks the ID
  register; that it is HVF that masks it is assumed).
- dep/linux, `arch/arm64/kernel/proton-pack.c`:
  `spectre_v4_get_cpu_hw_mitigation_state()` (l. 456): `SPECTRE_MITIGATED` only if
  `this_cpu_has_cap(ARM64_SSBS)`, else `SPECTRE_VULNERABLE`.
  `spectre_v4_enable_hw_mitigation()` (l. 531): touches SSBS only with the cap;
  with `spectre_v4_mitigations_off()` it sets `SCTLR_ELx_DSSBS` and `set_pstate_ssbs(1)`,
  otherwise `set_pstate_ssbs(0)` and says "SCTLR_EL1.DSSBS was initialised to 0
  during boot" (l. 549). `spectre_v4_enable_fw_mitigation()` (l. 612) needs the
  SMCCC ARCH_WORKAROUND_2 firmware call, absent here. The switches: `early_param("ssbd")`
  (l. 408, `force-on|force-off|kernel`) and `spectre_v4_mitigations_off()` (l. 417,
  `cpu_mitigations_off() || force-off`); both only act through the two functions
  above, which return early without the cap. Entry code: `apply_ssbd` in
  `arch/arm64/kernel/entry.S` (l. 114, used at l. 259 and 407) is the firmware
  path only (a branch over it that is patched to a NOP only when the firmware
  mitigation is needed). EL0: `start_thread()`
  (`arch/arm64/include/asm/processor.h` l. 340) calls
  `spectre_v4_enable_task_mitigation()` (proton-pack.c l. 656), which sets
  `PSR_SSBS_BIT` in the task's pt_regs unless `TIF_SSBD` (default policy
  "kernel"/dynamic): user code runs with SSBS = 1. EL1 gets SSBS from SCTLR_EL1.DSSBS
  (0 here) on exception entry (Arm ARM rule, assumed, consistent with the data
  below). `try_emulate_el1_ssbs()` (l. 514, traps.c l. 483) would emulate an
  undefined `msr ssbs` at EL1; it did not run (the instruction took effect).
- `msr ssbs, #imm` executes at EL0 (probe child: no SIGILL) and at EL1 on this
  hardware even though the ID register says SSBS is absent.

### Conclusion

The EL1/EL0 difference is PSTATE.SSBS: Linux enters EL1 with SSBS = SCTLR_EL1.DSSBS = 0
(the "no speculative store bypass" mode) and gives user tasks SSBS = 1, and with
SSBS = 0 this core serializes a load behind an older store to the same address
(~6.7 cycles per RMW unit, 1.5 ns for a bare `ldr;str`), while with SSBS = 1 a
single RMW costs one cycle and a chain of k units costs ~1.5 ns per unit (the
EL0 figures). It is not the Linux mitigation proper: the kernel reports
`spec_store_bypass: Vulnerable`, detects no SSBS capability (the guest's
`ID_AA64PFR1_EL1.SSBS` reads 0), and `mitigations=off` / `ssbd=force-off` are no-ops
because `proton-pack.c` only sets DSSBS when the capability exists; the hardware
nevertheless implements the bit and `msr ssbs` takes effect at EL0 and EL1. Setting it
inside fragment runs (a per-run `msr ssbs,#1`/`#0` pair, 22 ns, or DSSBS globally,
which also changes the kernel's own Spectre-v4 posture) removes most of the
slowdown of the budget chain (calls 4.1x -> 1.9x, byte copy 6.5x -> 1.25x, hash
2.2x -> 1.0x) without any translator change; PAN windows (simd32, 32x) are
unaffected. The earlier ranking changes accordingly: the budget-counter fixes
(flag poll, register counter) now matter for the residual 1.5 ns/unit of two or more
chained units and for strlen (0.98 against 0.33; the mirror loop reaches 0.5,
that gap is unexplained), not for the 6.7-cycle forwarding stall.

### Not verified

- Security: SSBS = 1 inside fragments (or kernel-wide) re-enables speculative store
  bypass in kernel mode for verified user-controlled code; not analyzed, and rule 9
  (confidentiality) does not model speculation.
- That it is HVF that hides FEAT_SSBS; behaviour on bare metal arm64 or other cores
  was not measured. The Arm ARM exception-entry rule (PSTATE.SSBS = DSSBS) is
  taken from the architecture, not read from the tree.
- DSSBS was set on the 4 vCPUs through `on_each_cpu` after boot only; the 2-boot
  code_speed medians come with the host load stated above.
- `exp_strlen_rmw_s0/s1` at EL1 in the full-set runs are invalid (an earlier entry,
  `exp_rmw1_uslot`, overwrites the first source byte); the rows above use the runs
  of `exp_strlen_rmw` / `_s0` / `_s1` made first in ub-dssbs1/2 and the EL0 ones.
