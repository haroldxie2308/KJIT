# 2026-10-10

## 09:05 +0800 — Why translated fragment code is slower than native: root cause

Commit: a518d03 (branch `exp/frag-speed`, experiment-only, not merged)

Question: `code_speed` (journal 2026-10-09, "Why KJIT does not reach Userspace
Bypass's speedups") measures fragment code 2.2x-34x slower than native. Which
emitted instructions cost the time, per symptom? Hypotheses to confirm or refute:
PAN windows are expensive for q copies; calls pay budget + dispatch template +
target materialization; back-edges pay the budget read-modify-write (RMW)
through memory; byte loops pay LDTR splitting and reg-virt fills/spills.

### Method

1. Emitted fragments. New fixture `tests/arm64/code_speed_kernels.s` (the hot loops
   of `code_speed.c`, n small) and an experiment-only bin
   `harness/src/bin/dump-fragment.rs` that runs cfg -> rephrase -> reg-virt ->
   layout and prints, per final word, the `RephrasedInsnKind` and original PC;
   disassembled with `llvm-mc`. Dumps: `.kjit/build/frag-dumps/frag_*.txt`
   (`fragdump.sh <case>`; `ENTRY_SYM=cs_leaf` for the callee fragment).
2. Microbenchmarks that execute those exact instruction sequences, ablated:
   `tests/guest/exp_kernels.h` (assembly, generated from
   `.kjit/build/frag-dumps/kernels.S`), `exp_table.h` (list), `exp_el0.c`
   (runs them at EL0), `exp_el1.c` + EXPERIMENT block at the end of
   `kjit_glue.c` (debugfs `exp_bench`: the same kernels at EL1 with IRQs off and
   `kernel_neon_begin`, user buffers `mlock`ed, `ktime_get_ns`). Median of 7 runs of
   ~20 ms; the table gives the median of 3 boots (spread < 1.5% unless noted).
   Cycle time from 8 dependent `add`s per trip: 0.32 ns (3.1 GHz).
3. Fragment reference: `ub-bench.sh code 7` on this tree, 4 boots (slope per unit,
   median): calls 6.33, strlen 2.14, copy 2.10, hash 2.14, copy16 2.11 (per 16 B),
   simd32 15.44 (per 32 B) ns; native slopes 1.54 / 0.32 / 0.32 / 0.96 / 0.39 /
   0.43 (same boots; copy16/simd32 native per 16/32 B from the slope x unit).

Host: M1/HVF, 4 vCPUs, kjit-guest, KJIT disabled for the exp runs (debugfs
enable=0 auto=0). `pgrep qemu-system` empty before each boot; load1 at boot
start 5.92 / 4.43 / 3.96 (expA1-3), 5.26 / 4.09 / 3.76 (codeB1-3), 5.91
(code-base1).

### 1. Emitted sequences (hot loop, per original instruction -> emitted)

Roles: U user op (LDTR/STTR), W PAN toggle, R range check, B budget, D dispatch,
A align check, F fill/spill.

- strlen `ldrb w6,[x3],#1 ; cbnz w6` (2 insns) -> `ldtrb w6,[x3]` U, `add x3,x3,#1`,
  `ldr x12,[sp,#192] ; sub x12,x12,#1 ; str x12,[sp,#192] ; cbz x12,<stub>` B,
  `cbnz w6` = 7 insns.
- hash (5) -> 10 (ldtrb+add, 3 ALU, subs, B x4, b.ne). copy (4) -> 10 (ldtrb+add,
  sttrb+add, subs, B x4, b.ne).
- copy16 `ldp/stp x` + subs + b.ne (4 per 16 B) -> 15: `ldtr x13`, `ldtr x12`,
  `mov x6,x13`, `add`, `str x12,[sp,#24]` F, `ldr x12,[sp,#24]` F (the program
  uses x13, stack-backed), `sttr`, `sttr`, `add`, subs, B x4, b.ne.
- simd32 `ldp q0,q1,[x3],#32 ; stp q0,q1,[x7],#32 ; subs ; b.ne` (4 per 32 B) -> 20:
  per access `mov x12,x3 ; ubfx x13,x12,#48,#8 ; cbnz x13 ; msr pan,#0 ; ldp q0,q1,[x12] ;
  msr pan,#1 ; add x3,x3,#32` (R, W, U, W) twice, then subs, B x4, b.ne.
- calls (14 insns per call+return) -> 64: caller `mov x0,x5` (1), B x4, target
  `movz/movk x13` x4 D, link `movz/movk x30` x4, template main-probe hit path 9
  (`ldr x12,[sp,#200] ; ubfx ; ldr ; cbz ; ldr ; sub ; cbnz ; ldr ; br x12`) D; callee
  fragment 21 (3 align pairs `and x12,x17,#15 ; cbnz`, 2 sttr, 1 sttr, 2 ldtr + 1
  ldtr, ALU) + B x4 + `mov x13,x30` + template 9; caller after the resume:
  `mov x5,x0 ; subs ; B x4 ; b.ne`. Three budget units per call iteration (bl, ret,
  back-edge) = 12 of the 64 instructions, all on one memory slot.

| 2 units on 2 slots / 4 units on 4 slots (per unit) | 1.040 / 0.552 | 0.241 / 0.201 |

| register counter (`sub;cbz`), 1 / 3 units | 0.320 / 0.360 | 0.320 / 0.361 |

(The EL0 column is exp_el0 in the same boots.) At EL0 a single RMW per

### 3. Per symptom (EL1 microbench vs fragment; ns per unit)

| symptom | native | + LDTR/add/etc | + budget RMW (= model) | fragment | residual |
|---|---|---|---|---|---|
| strlen (per byte) | 0.324 | 0.323 (`ldtrb`) | 2.129 | 2.14 | +0.5% |
| copy (per byte) | 0.319 | 0.319 | 2.087 | 2.10 | +0.6% |
| hash (per byte) | 0.946 | 0.947 | 2.218 | 2.14 | -3.5% |
| copy16 (per 16 B) | 0.376 | 0.536 (the x13 spill) | 2.083 | 2.11 | +1.3% |
| calls (per call) | 1.582 | 1.575 (ldtr, align, reg budget, bl/ret) | 6.247 (with dispatch template: 2.283 + 3.96) | 6.33 | +1.3% |
| simd32 (per 32 B) | 0.396 | 0.553 (range checks + moves) | 15.26 (15.35 without budget) | 15.44 | +1.2% |

- Byte/pair loops (strlen, copy, hash, copy16): the loop is one budget unit per
  trip; `strlen_rmw` 2.129 vs `strlen_reg` 0.320 (register counter) vs
  `strlen_ldtr` 0.323. Root cause: the budget counter's store-to-load chain through
  `[sp,#192]` costs 2.1 ns per unit at EL1, which exceeds the loop's own 0.3-0.95 ns.
  LDTR cost nothing (hypothesis refuted); fills/spills cost 0.16 ns/trip in
  copy16 only (x13 stack-backed).
- Calls: three units per call+return on one slot = 3 x 2.08 = 6.25 =
  `calls_bud_only` (native code + the three budget units): 6.407. Removing only
  the budget: 2.051 (`calls_nobud`); register counter: 2.283. Dispatch template
  with the register budget costs +0.71 ns per call (2.283 vs 1.575 with bl/ret);
  LDTR + align checks cost 0 (1.575 vs native 1.582). calls2 (5 units): 5 x 2.07
  = 10.4 vs fragment 10.55. Hypothesis "dispatch template + target materialization
  dominate": refuted, they are 0.71 of 6.25.
- simd32: one `msr pan` costs 2.07 ns (pair 4.13); a window around one access
  7.66 (the access cannot overlap the surrounding PSTATE writes: +3.5); two
  windows 15.3; the budget (2.1) hides under them (win1 15.26 with, 15.35 without).
  One window around both accesses: 7.68. Range checks and moves alone: 0.553.
  Root cause: PAN is switched with `msr` per access and each window costs about 7.5 ns.

One-sentence root causes: (1) tight loops, calls: the budget counter RMW on one
frame slot forms a loop-carried memory dependence of about 2.1 ns per budget unit
at EL1 (3 units per call = 6.3 ns, 1 per loop trip = 2.1 ns); (2) q copies: two
serializing `msr pan` per access, about 7.5 ns per window.

### 4. Fix candidates (estimates from the microbenchmarks, not implemented)

Gain = EL1 microbench of the same sequence with the change; slowdown vs native in
parentheses.

| # | change | gain | contract impact | risk |
|---|---|---|---|---|
| 1 | Budget exit by polling the task's pending flags: `mrs x12,sp_el0 ; ldr x12,[x12] ; tbnz x12,#bit` (no store, no loop-carried chain) | strlen 2.13 -> 0.32 (1.0x), copy16 2.08 -> 0.60, calls 6.25 -> 2.41 (1.5x), simd32 unchanged | rewrites A6 (budget = pending-work flags, not a count): prologue slot 192, rule 6 sequence, `Budget` semantics, harness instance-cap/determinism (flag injected at instance k), new `MRS sp_el0` form and a kernel load in the verifier (rule 5 and taint rule 9), depends on `thread_info` layout; run length bounded by tick/signals, not 4096 units | medium-high |
| 2 | Register counter in a reserved physical register | same as 1 for loops (0.32), calls 2.28 | reg-virt gives up one more register (its user register becomes stack-backed: that register's accesses then pay the same chain if hot); prologue/epilogue | medium |
| 3 | One slot per budget site | calls 6.25 -> 2.52; single-site loops unchanged (2.1) | budget bounded per site (sum = sites x N); frame slots | low, small gain |
| 4 | Coarser accounting (one RMW per k units) | 2.1/k per trip if the translator unrolls; none otherwise | needs unrolling or loop-level charging; ret cannot be uncharged (`adr x30,.; ret` loop) | high effort |
| 5 | One PAN window for adjacent SIMD&FP accesses of consecutive original instructions in a block | simd32 15.3 -> 7.7 (34x -> ~17x) | verifier: a window covering several base-only accesses, a range check per access before `msr pan,#0`, no branch inside, PAN stub for every access; fault-site table | medium |
| 6 | Lower ldp/ldr/str/stp q and d through LDTR/STTR plus `fmov`/`mov v.d[1]` (no PAN) | simd32 15.3 -> 1.10 (2.8x) | loses 16-byte single-copy atomicity of a q access and the fault footprint rules; code size x3; removes the PAN window for plain forms (LD1/ST1 and LSE atomics keep it) | medium-high |
| 7 | Hoist PAN off across a loop | simd32 -> 0.553 + budget | verifier PAN-state dataflow, every exit must restore PAN | high |
| 8 | In-fragment direct `bl` without the template | at most 0.7 ns per call+ret pair (after fix 1/2) | rule 7/9 for a direct branch to a label of the same fragment (callee must be in the fragment) | medium |

Ranking by gain/risk: 1 (or 2), then 6 or 5 for SIMD, 3 (only if 1/2 are
rejected), 8, 7, 4. Fixes 1/2 alone move the code_speed slowdowns to about: strlen
1.0x, copy 1.0x, hash 1.0x, copy16 1.6x, calls 1.5x, simd32 still 34x.

### Not explained / not verified

- Why a loop-carried RMW through memory is 6.7 cycles at EL1 but 1 cycle at EL0
  (same core, same boot; slot address, PAN and kernel/user memory ruled out by
  `rmw1_sp` and `rmw1_uslot`). The mechanism (a core feature not applied at EL1, or
  guest-mode related) was not identified; only EL0 and EL1 in this guest were
  measured. It matters for fix 1/2: they remove the chain regardless.
- `msr pan` serialization is inferred from timings; the 3.5 ns the access adds
  inside a window is not explained either.
- The microbenchmarks are hand-assembled mirrors of the dumped sequences (offsets
  of branches differ, the miss paths are stubs), not translator output; the fragment
  figures come from separate runs and agree within 3.6% (largest: hash).
- No fix was implemented, assembled with the verifier or run through a fragment;
  the flag-poll semantics (bit choice, runs bounded without a pending tick, RCU/
  softlockup interplay, `PREEMPT` kernels) are assumptions. Bit 40 was polled in
  the benchmark, so the flag never fired.
- Not analyzed: `callsi`/`calls2` dumps exist but were not microbenchmarked
  separately (calls2 predicted from units: 5 x 2.07); `foot`/`footl`.
- Host noise: load1 3.4-5.9 during the runs; other host load not controlled.
- A first hung guest (expA1, `exp_rmw_every4` with an `outer` that was not a
  multiple of 4: the kernel looped forever) was killed and the kernel fixed
  (`b.hi`); its partial log was discarded with its run directory.

Review note (architect): the unexplained EL1/EL0 gap of the memory
read-modify-write chain (~6.7 cycles per unit at EL1, ~1 at EL0, same boots,
any memory type) fits a speculative-store-bypass mitigation that applies only
to the kernel: arm64 Linux runs EL1 with SSBS clear (Spectre v4), which stops
loads from issuing ahead of an older store to the same address, so the counter
chain waits for each store. Untested hypothesis: check
`/sys/devices/system/cpu/vulnerabilities/spec_store_bypass` in the guest and
re-run the RMW chain with `ssbd=force-off` (or `mitigations=off`). If it holds,
any frame-slot read-modify-write in fragment code pays it, and fixes 1/2 (no
memory counter) are the right direction regardless of the mitigation setting.
